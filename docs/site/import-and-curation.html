Who may create a person, and what a bulk import does

Person files are the human-curated tier, so folk has to decide who may bring a new one into existence. By default only a human does. A collection can state on disk that an automated process may create files in it. A bulk import is the first automated writer, and it is built to fail one row at a time rather than the whole batch.

Status, at a glance. Implemented: the per-collection curation gate, the batch import runner with skip-and-report, and person-file minting gated by that curation. Implemented as a skeleton: the directory adapter's parsing, with no live fetch. Open: identity resolution beyond the current heuristic, which is a design with no code behind it yet.

Curation: human by default, agent by declaration

A collection may place a COLLECTION.json file in its own root. Only the exact value "agent" opts in:

{"curation": "agent"}

Anything else resolves to human: a missing file, unreadable or malformed JSON, a non-object document, or any other value. Folk fails closed, so a typo in the file leaves the collection protected. The file is read in one place, and nothing in the code names a collection.

The gate covers creation by a machine and nothing else. A human may create or edit any file in any collection, whatever the file says. Once a human edits an agent-created file, it belongs to that human, and by convention automated writers stop rewriting it. Folk does not enforce that convention in code. A machine caller creates a file only through one function, which checks the slug, checks the gate, and refuses to overwrite an existing file. The refusal is an error the caller sees, not a quiet skip.

The shipped repository includes no collection descriptor, so every collection in it resolves to human. Opting a collection in is a one-line file that its owner places on purpose.

Bulk import: one row fails alone

A bulk import is a batch of already-shaped observation events, produced by an adapter from a source that has no conversation and no model step. Each event goes through the same lint as any other write, and import_batch wraps that lint in a loop that keeps going after a failure. A bad row is reported with its reason, and its neighbors are still appended. This is a different policy from promotion, which quarantines a whole session because one model-written event may signal that the rest are suspect. Rows from a scrape share no author and no reasoning, so one bad row says nothing about the others.

Three details matter for anyone running a batch. Person-file minting happens only for an event that appended, only for a subject the caller gave a display name for, and at most once per subject in a batch. Minting is best-effort: a refused, invalid, or already-existing file leaves the event appended. The batch function does not run the rebuild, so the operator runs it as a separate step.

Organizational structure is modeled as Loci rather than bare strings. A directory record that places a person in a department produces a works_at edge whose object is locus:<department>, so the department gets a file, can be shown, and can carry its own cast. The shape of that file is a ## Locus Type section: a single free-text value that folk parses and never validates, so a department, a lab, or a shared resource are labels a writer chooses. The import does not create department files. A writer does that by hand, once per organization. This classifier is implemented and tested, but its design has not yet been confirmed by the maintainer.

The directory adapter, honestly

The directory adapter in folk/sources/directory_scrape.py is a skeleton. Its parse() turns one raw record into observation events, one for a title and one for a department, and it is tested. Its fetch() is a stub that raises NotImplementedError, because a real fetch needs an HTTP client and an HTML or JSON parser that folk does not depend on. The adapter is deliberately absent from the transcript-source registry, because that registry feeds the model-based promotion path and a bulk import uses none of that.

Identity resolution: open, and not yet built

Deciding whether a scraped name is someone folk already knows is harder than appending rows. Today it rests on one heuristic. folk lookup compares token sets of the two slugs and returns the single best candidate at or above a 0.6 Jaccard overlap. The design document that replaces it is a living draft with no code behind it: there is no identity module, no alias section, and no identifier section yet.

The draft lists several defects in the heuristic. The near-duplicate check in lint runs only on the object of an event, which the code confirms, so a new person who appears as a subject is never flagged. The type prefix, such as person, counts as a shared token in every comparison, which inflates every score. A shared generic token, such as a title, can produce a match on its own. Two people whose slugs differ only by a suffix are proposed again on every run, because nothing records that they are different.

The draft's direction is to stop scoring and start recording. A human answer would be stored in the person file as an alternate name or a stable external identifier, so the next lookup is an exact match and the same question is never asked twice. Candidate generation would be a set of named, deterministic matchers, ordered by configuration, and no combined score would be produced. Machines would never merge two files, and an ambiguous case would stay ambiguous until a human decides it. Open questions for the maintainer include whether the alternate-name and identifier data are one section or two, whether declining a duplicate proposal should leave the facts it came with in place (the draft says the current behavior does not), and whether a re-scrape of a known person may update that person's file.

The scope boundary

folk owns identity and relationships that stay true whichever project is looking at them. A project owns everything specific to itself, and it refers to folk's person: and locus: slugs rather than copying its own content into folk. This is the same line that appearance draws within a single person: what is true of the figure across every frame belongs to folk, and what is true in one frame belongs to the project.

  • folk's: who a person is, their durable facts, their organizations and their curated connections.
  • a project's: its notes, its protocols and results, its tasks and deadlines, and any record that has to show a fact existed unaltered at a given time. folk's redaction mechanism is built to remove a fact on request, which is close to the opposite guarantee.
  • the seam: a project writes its own edges back into folk as observation events and keeps everything else in its own record. A Locus description can drift toward project narrative, and that is a known failure mode rather than a current violation.
