Three records, one authority each

Everything folk stores lives in exactly one of three places, and each place is the single authority for one kind of truth. This is invariant #1, and it is the load-bearing wall: every other design decision leans on it.

Why a disposable cache is a feature

Most memory systems accumulate state that slowly becomes its own authority: a database that can't be regenerated, embeddings nobody can audit, scores that drifted. folk avoids this. The index is defined as a pure projection of the other two records, which buys three things:

  • Migration is trivial. Change the index record shape? Delete the file, rebuild. That's the entire migration story, and it has already been used in production.
  • Corruption is impossible to keep. Any bad state in the index has a half-life of one rebuild. This is also why nothing but rebuild may write it — a directly-written index line is silently destroyed by the next rebuild, so "write the index directly" isn't a shortcut, it's a data-loss bug.
  • Agent memories survive anyway. Deleting the index does not delete what agents recorded — that lives in the journal, and replay brings it back. The cache being cheap is what makes the journal being sacred affordable.
Invariant 2

Nothing but folk index --rebuild writes the index. Agents and commands write person files (human-driven) or append journal events — never index lines.

The rebuild is a pure function

Rebuild parses person files from every configured collection (human tier), replays every journal segment across every registered root (the machine tiers), applies review verdicts, redactions, and slug aliases as projections, and writes the sorted result. There is no LLM, no wall clock, no filesystem-order dependence anywhere in this path — run it twice and the output is byte-identical. That property is a hard test in the suite, not an aspiration.

What an index record looks like

{"s": "person:sam", "p": "works_at", "o": "org:studio-b",
 "tier": "observed", "col": "personal",
 "src": "msg:20260514_025200_91059e71#12",
 "when": "2026-05", "last_reinforced": "2026-07-14T03:11:02Z"}

Two derived fields are worth noticing. tier replaces the old prov/conf pair — see Trust tiers. last_reinforced is the max timestamp across all journal events asserting the same triple: re-observing a fact in a later conversation refreshes it automatically, and nothing ever has to write "freshness" anywhere. The Archivist's decay lens reads this field; it never writes anything.

Where the human tier comes from

A person file is deliberately boring markdown. Every ## section is a convention, not a schema — folk parses the ones it knows and leaves the rest alone:

# Toru Watanabe

Narrator and protagonist of Norwegian Wood.

## Archetype
quiet observer

## Voice
understated, first-person, wry

## Associations
- [Norwegian Wood](work:norwegian-wood) — appears_in

## Tags
character

## Defining moments
- ...

Commands like folk link and folk tag edit these files (then trigger a rebuild) — they never touch the index directly. And when the review queue accepts a bedrock suggestion into a person file, it shows the exact diff and asks: the tool is a typist, not an author.

The rule of thumb

When deciding where any new piece of state belongs, ask: is it a human judgment (person file), a thing that happened (journal event), or derivable from the first two (rebuild projection)? If it seems to need two homes, the design is wrong.
