Appearance: a durable brief for a figure

A person or Locus can carry a physical description that a consumer can address field by field. folk stores the description and returns it; it never generates, measures, or compares an image. Consistent text is not consistent likeness, and the page is written around that limit.

Status. The ## Appearance section and the ## Appearance: <name> checkpoints are implemented in folk/person.py and folk/render.py, with tests in tests/test_appearance.py. Reference images are a draft and not implemented: nothing in folk reads a reference, and folk render emits no reference key. The reference-image design and its open questions are listed at the end of this page.

What the section is, and what it is not

A person file gets an optional ## Appearance section of - label: value lines. It is Bedrock: a human writes it, and nothing mechanical writes it in batch. Folk does not validate the label names. The conventional labels (build, hair, face, dress) are guidance for writers and consumers, not a schema, and no label name appears anywhere in folk's code. A line that does not match the - label: value pattern is kept as free text rather than dropped, so a paragraph written under the heading still reaches consumers.

The section answers one question: is this true of the figure whenever you meet them? Build, face, hair, and a characteristic dress that is part of the identity belong here. What is true only in one piece or one shot does not: a pose, an expression, what the figure is holding, the wardrobe for one scene, and any rendering-only negative hints. The test is whether the value changes between two frames of the same piece, and the label does not decide it.

Honest limit

Text is not likeness. Handing the same brief to an image model in twelve prompts produces twelve related-looking strangers. Face-level consistency comes from a reference image, a trained embedding, or a fixed seed, all of which live on the rendering side. What the brief buys is one place where the description is written once, addressed by field, and inherited by every consumer, so drift comes from the model and not from several writers describing the same person differently.

Checkpoints: states that are all true at once

A figure is sometimes defined in more than one state that stays true permanently, such as a younger and an older presentation, or a formal and a working look. Those are not history. Nothing becomes wrong when the next state is reached, so editing the file would erase a fact that still holds. A checkpoint section, ## Appearance: <name>, holds one such state. The name is an opaque string. Folk does not sort names, compare them, or read a date from them.

The merge is fixed and ordered. The base section comes first in file order. A label the checkpoint also states overrides the base value and keeps the base's position. A new label in the checkpoint is appended in the checkpoint's own order. Nothing is sorted, and the result is the same on every run.

The render surface

Two formats carry the brief. Both accept --checkpoint, and both are deterministic: two runs on unchanged input give identical output.

folk render person:sam --format dream --json                  # base section only
folk render person:sam --format dream --checkpoint winter --json  # base, overridden by the winter state
folk render person:sam --format soul --checkpoint winter       # persona view, same merge
  • folk render <ref> --format soul places an Appearance block after Voice in the generated persona view. An empty section is omitted and no empty heading is written.
  • folk render <ref> --format dream --json adds keys after description, in this order: appearance (labelled pairs), appearance_text (the same content flattened to one line), appearance_fingerprint, checkpoint (the selected name, or an empty string), and checkpoints (every available name, always present, so a consumer can list them in one call).
  • folk show lists the checkpoint names but not their contents. The summary stays a summary, and a checkpoint is shown only when it is asked for by name.

The fingerprint is what makes a render attributable. A rendering consumer that records which brief it used can record the fingerprint, and a later reader can tell which version of the brief produced which image without reconstructing the text. An empty brief gives an empty fingerprint, so an undescribed figure is not confused with a described one.

Reference images: draft, not implemented

The reference-image design is a separate draft. It proposes a typed ## Reference section that stores a pointer to an image and never the image itself, a per-collection descriptor that decides whether a likeness may be emitted to a renderer, and a choice of where the bytes live. Its decision about where the bytes live is a human decision and is still open. Nothing in this section is in the code today. Until that draft is confirmed, a figure's likeness is described in words only, and that is all folk will hand a renderer.

What is not designed

  • Interpolation and age progression. Folk does not generate a state between two checkpoints or beyond the last one. A generated text brief would arrive as a proposal for a human to accept, and a generated image would be a render, not a folk fact.
  • Scoring images. Folk never opens an image file. The evaluation script, scripts/appearance_eval.py, checks only deterministic properties of the text (determinism, coverage, propagation, stability) and imports nothing that reads an image. Whether a render looks like its figure is left to a human.
  • Appearance history. There is no timeline and no validity window on any trait. A checkpoint is a named state, not a date, and a trait that has really changed is edited in the file while git keeps the earlier text.
