# Unicode slugs in the journal — scoping the remaining half of the slugify fix

**Status:** decided and implemented (2026-08-31) — narrow fix, see Revision log. Written to close the gap flagged in commit `febcd32` ("slugify(): fold Latin diacritics, preserve non-Latin scripts"), which deliberately left journal.py untouched: "journal.py's own separate, stricter SLUG_RE and its two ad hoc ASCII-only slugify duplicates ... That's the canonical event-schema format, a bigger and more consequential change than this utility fix — flagged for a separate, explicit decision rather than silently widened here." This doc was that separate decision.

**Context:** `folk/graph.py` `slugify()` (the just-landed fix); `folk/person.py` `SLUG_RE`/`TYPED_REF_RE`/`PERSON_FILE` (widened in the same commit to accept what `slugify()` now produces); `folk/journal.py` `SLUG_RE` (line 24), `_person_triples`/`_locus_triples` (lines ~460, ~502, the two ASCII-only `re.sub` fallbacks); `docs/design/journal-schema.md` line 18 (normative slug-format text); `docs/design/identity-resolution.md` (already names these exact two journal.py call sites as needing to route through a future single normalization authority — see its Decision 2 and scope item 1).

## Why this is a real gap, not a hypothetical

A person or locus file can now carry a non-Latin or diacritic display name — `graph.slugify()` and `person.SLUG_RE` handle that correctly as of `febcd32`. But `## Associations` entries that name someone by free text rather than an explicit `type:slug` ref (the common case when a human writes `- [Jane Smith] — colleague` instead of looking up the slug) are resolved at replay time by `journal._person_triples`/`_locus_triples`, using their own inline `re.sub(r"[^a-z0-9]+", "-", name.lower())` — not `graph.slugify()`. For a non-ASCII name this strips everything to near-nothing instead of folding it the way the real person file's slug was derived, so the association's object slug silently fails to match the actual person and the edge is lost (or worse, several different non-Latin names all collapse to the same near-empty slug and get merged in the graph). `journal.SLUG_RE` would separately reject a correctly-folded non-ASCII slug if it ever reached the lint path, since its body pattern is `[a-z0-9][a-z0-9-]*` — ASCII-only, stricter than `person.SLUG_RE`'s now-Unicode-aware `\w[\w-]*`. Both problems are inconsistency with the fix already landed elsewhere, not new behavior to invent.

## What's involved

**1. Two independent code changes, needed together.** Loosening `journal.SLUG_RE` alone doesn't fix anything — it just stops catching the mangling that `_person_triples`/`_locus_triples` still produce. Fixing only the `re.sub` calls without loosening `SLUG_RE` means the lint would then reject the correctly-folded slugs it just started emitting. Both have to land in the same change:
   - `journal.SLUG_RE`: widen the slug-body half to Unicode-aware `\w[\w-]*` (mirroring `person.SLUG_RE`/`TYPED_REF_RE`), keep the `type:` prefix as ASCII `[a-z]+` — types are controlled vocabulary (invariant 7), not user text, and there's no i18n argument for widening them.
   - `_person_triples`/`_locus_triples`: replace the inline `re.sub` with the same NFKD-fold-then-preserve-remaining-scripts algorithm `graph.slugify()` uses, so a free-text association name resolves to the *same* slug the referenced person's file actually has.

**2. The import direction blocks the obvious fix.** `graph.py` already does `from . import journal as journal_mod`, so `journal.py` cannot import `graph.slugify` at module level without a cycle. Three ways to resolve this, in increasing order of durability:
   - A local (function-scoped) `from . import graph` inside `_person_triples`/`_locus_triples`. Smallest diff, but has a lower-level module reaching up into a higher one, and it's the kind of shortcut that tends to calcify.
   - Extract `slugify()` out of `graph.py` into a new dependency-free leaf module (e.g. `folk/slug.py`), imported by both `graph.py` and `journal.py`. Clean, but creates a module that `identity-resolution.md` (below) already plans to obsolete.
   - Do neither now and fold this into `identity-resolution.md`'s already-scoped `folk/identity.py` centralization, whose v1 scope item 1 explicitly says the new module becomes "the *only* normalization authority" and names these same two journal.py call sites as callers. That doc is an unconfirmed, in-progress design sprint, not yet buildable on its own timeline.

**3. `journal-schema.md` needs a text update, not just the code.** Its line 18 is normative and currently reads "Slugs are lowercase ascii, hyphen-separated, type-prefixed" — per CLAUDE.md's rule that lint is this doc's executable form and whichever disagrees gets fixed, the doc text has to change alongside `SLUG_RE`, to something like "the type prefix stays lowercase ascii; the slug body may contain any script's letters/digits after diacritic-folding — see `docs/design/unicode-slugs.md`."

**4. Nothing else in the lint path needs to change.** `_near_duplicate`/`_slug_tokens` (journal.py ~246–265) tokenize by splitting on `[-:]` and compare token sets by exact equality — no ASCII assumption, works over any script as-is. `MSG_SRC_RE`, the `conv:`/`msg:` carve-out in the lint loop, and `compute_id`'s hashing are all format- and script-agnostic already.

**5. No migration needed.** Journal segments are append-only (invariant 3); loosening `SLUG_RE` only affects what's accepted going forward, and existing ASCII slugs stay valid under the wider pattern. `folk index --rebuild` stays a pure deterministic script either way (invariant 4) — NFKD folding is pure stdlib, no clock, no LLM.

**6. Test coverage.** `test_graph.py` already picked up diacritic/non-Latin cases in `febcd32`; `test_journal.py` needs the parallel case that's actually the bug here — a person or locus file with a non-Latin display name, referenced by a *different* file's free-text `## Associations` entry (no explicit ref), asserting the derived object slug matches the referenced file's real slug — plus a lint fixture confirming a correctly-folded non-ASCII slug passes `SLUG_RE` and an ASCII-violating type prefix still fails it.

## Related but separate — digger's multi-artist-per-track problem

Digger (a sibling project reconciling music metadata) has an analogous-looking but distinct problem: `docs/design/nas-artist-inference-backfill.md` Part 7 ("collapsed rows") handles track files whose directory legitimately spans ≥2 distinct artists, which must be *split* into per-artist rows before any name matching happens at all. `identity-resolution.md`'s own Deferred section already draws this line correctly: identity resolution (this doc's concern, and that doc's) is "is this name string the same *one* entity as an existing one"; digger's problem is "this one record actually names *multiple* entities and has to be segmented first." Digger's actual mechanism — AcoustID audio-fingerprint disambiguation — is audio-content-specific and doesn't generalize to folk's text-only domain, so it isn't reusable prior art for the matcher design here.

It did surface a real, concrete parallel in folk itself, though: `person._parse_associations` treats one `## Associations` line as one `name` string with no splitting, so a human-written line like `- [Jane & John](work:band) — bandmates` produces a single association named `"Jane & John"` — and that string lands in the exact same two call sites this doc is fixing (`_person_triples`/`_locus_triples`). Today, and after this fix, that still slugifies into one fake merged "person" rather than two real associations. This is a **segmentation bug, not a Unicode-folding bug** — it would occur identically for `"Jane and John"` in pure ASCII — so it is explicitly out of scope for the fix below. Flagged here so it isn't lost: worth its own design note (or a line in `identity-resolution.md`'s Deferred section, since it's the same "split before resolving" shape as digger's Q1) before anyone builds an importer that writes free-text multi-name associations at scale.

## The actual decision for the maintainer

Not whether to do this — the inconsistency is real and `identity-resolution.md` already independently arrived at "these two call sites should route through one normalization function." The open question is sequencing: fix `journal.py` narrowly now (small diff, `folk/slug.py` or a local import, low risk) and let `identity-resolution.md` subsume it later when that sprint lands, versus holding this fix until `identity.py` exists so the normalization authority is only written once. Given `identity-resolution.md` is explicitly an unconfirmed, in-progress "living reference" with no landing date, and the mangling is a live correctness bug today (silently dropped or wrongly merged graph edges for any non-Latin name used in free-text association form), the narrow fix now seems like the lower-risk default — but it's the maintainer's call, not a default to assume.

## Open questions — resolved

1. **Fix now (narrow) or defer to `identity-resolution.md`'s centralization? → Fix now.** `identity-resolution.md`'s v1 scope doesn't cover the multi-entity/segmentation case either (see above), so waiting for it to land wouldn't have closed that gap anyway — it only reinforced that this fix and that sprint are separable, not sequenced.
2. **New `folk/slug.py` leaf module, or a function-scoped import? → New leaf module.** `slugify()` moved out of `graph.py` into `folk/slug.py` (no folk imports, dependency-free); `graph.py` now does `from .slug import slugify` (re-exported, so `graph.slugify(...)` call sites and `test_graph.py` are unaffected); `journal.py` imports the same function directly. `folk/identity.py`, if `identity-resolution.md` ever lands, absorbs `folk/slug.py` at that point rather than the reverse.
3. **Does `journal-schema.md` change in the same commit? → Yes**, done alongside the code.
